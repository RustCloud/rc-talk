# Предложение: сообщения между пользователями, события и звонки для плагинов

Статус: черновик для обсуждения, 2026-11-16. Повод — плагин общения `rc-talk` (чат и звонки, аналог
Nextcloud Talk), но предлагаемые возможности общие: каждую используют и другие плагины.

## Коротко

Сейчас плагин не может передать данные другому пользователю (кроме общих папок AppData, которые
выдают по одной через диалог), разбудить его страницу без опроса и включить камеру. Предлагается
добавить пять возможностей, не меняя модель песочницы: личные данные остаются в AppData
пользователя, всё новое — отдельные пункты манифеста, которые утверждает администратор.

| # | Изменение | Объём | Что даёт |
|---|-----------|-------|----------|
| 1 | Импорт `mailbox`, событие задач `mailbox`, SSE панели, значок и `ring` | средний | доставка между пользователями, события в реальном времени, простые уведомления, сигнализация звонков |
| 2 | `permissions.media` (после эксперимента; запасной путь — отдельный origin страниц плагинов) | малый | камера, микрофон, показ экрана |
| 3 | `appdata.write-if-match` | малый | запись в AppData без потери параллельных изменений |
| 4 | `permissions.connect` в CSP страницы | малый | соединения страницы с утверждённым сервисом (LiveKit) |
| 5 | Вложения в `mailbox` (`attach`) | средний | файлы в сообщениях |
| 6 | TURN-серверы: настройки, временные учётные данные, режим «только через TURN» | малый (в плагине), по желанию — в ядре | звонки через NAT, корпоративные сети и мобильный интернет |

Пункты 1–3 и 6 нужны для чата и звонков один на один, 4 — для групповых звонков, 5 — для вложений.
Предлагаемая версия API — `0.2.19` (только добавления, плагины на прежних версиях работают).

## Принципы

1. **Песочница не ослабляется.** Новый экземпляр на запрос, лимиты, CSP `sandbox`, отсутствие cookie
   и утверждение прав остаются как есть.
2. **Возможность — по разрешению.** Каждая новая возможность объявляется в манифесте, видна
   администратору при включении и при обновлении требует нового подтверждения, как `network` и `frame`.
3. **Общие примитивы, а не исключения под один плагин.** Если для плагина хочется сделать
   исключение, значит, не хватает примитива.
4. **Личное — у пользователя.** Данные человека лежат в его AppData и его квоте. Сервер хранит только
   то, что в пути (письма до подтверждения), и сам удаляет это.
5. **Тяжёлое и долгоживущее — отдельным сервисом**, которому доверяет администратор (coturn, LiveKit),
   а плагин — связующее звено с правами.

## 1. Почтовый ящик плагина (`mailbox`)

### Задача

Алиса пишет Бобу. Плагин работает от имени Алисы и может писать только в её AppData. Варианты,
которые есть сейчас, плохи:

- **Общее хранилище плагина (`storage`).** Документация запрещает класть туда личные данные, сервер
  этого не проверяет; нет квот, права проверяет только плагин, администратор может стереть данные.
- **Общие папки AppData (`shares`).** Каждому участнику доступ выдают через диалог, по одному и по
  имени; всё идёт в квоту владельца; удалили владельца — беседа исчезла у всех.

### Решение

Каждому пользователю в каждом плагине — ящик. Плагин отправителя кладёт письмо в ящик получателя.
Плагин получателя, **работая от имени получателя**, забирает письмо и раскладывает в его AppData.
Каждый хранит свою копию, в своей квоте; в чужую AppData никто не пишет.

### Контракт

```wit
interface mailbox {
    use types.{user};

    record letter {
        id: string,
        /// Отправитель. Проставляет сервер — пользователь запроса; плагин подделать его не может.
        %from: user,
        /// Что это для плагина: "msg", "msg.edit", "room.update", "call.offer"…; a-z0-9._-, до 64 байт.
        kind: string,
        /// До 64 КБ.
        data: list<u8>,
        /// RFC 3339, UTC. Письма одному получателю отдаются в порядке поступления.
        sent-at: string,
    }

    record options {
        /// Эфемерное письмо (сигнализация звонка): живёт не больше 300 с, потом удаляется,
        /// в ящике не копится.
        ttl-seconds: option<u32>,
        /// Панель покажет получателю всплывашку с этим текстом (до 100 символов), см. «Пробуждение».
        ring: option<string>,
    }

    variant error {
        no-user,
        /// Больше 50 получателей, слишком большое письмо, неверный kind.
        invalid(string),
        /// Отправитель превысил частоту отправки или ящик получателя переполнен.
        too-many,
        other(string),
    }

    /// Отправить письмо. `to` — id пользователей (из `letter.from` прежних писем) или имена.
    /// Неизвестное имя молча пропадает — ответ тот же, что и для существующего (как в app-shares).
    send: func(to: list<string>, kind: string, data: list<u8>, opts: options) -> result<_, error>;

    /// Письма в ящике пользователя запроса в этом плагине, не больше `limit`. Выданные письма
    /// «арендуются» на 60 с: другой экземпляр их в это время не получит; без `ack` они вернутся.
    fetch: func(limit: u32) -> result<list<letter>, error>;

    /// Письма обработаны — удалить.
    ack: func(ids: list<string>) -> result<_, error>;
}
```

Почему так:

- **`from` проставляет сервер.** На этом держится вся логика групп у плагина: «изменения состава
  принимаю только от владельца беседы», «правку сообщения — только от автора».
- **Аренда при `fetch`.** Письма может забрать и открытая страница пользователя, и фоновая задача;
  аренда не даёт обработать письмо дважды одновременно. Плагин всё равно должен быть идемпотентным по
  `letter.id` (аренда могла истечь посреди обработки).
- **Имена без перебора.** `send` на несуществующее имя отвечает так же, как на существующее, как уже
  сделано в app-shares.

### На сервере

- Таблица `app_mailbox(id, app_id, to_user, from_user, kind, data, created_at, expires_at,
  leased_until)`, индекс по `(app_id, to_user, id)`. Удаление аккаунта — каскадом в обе стороны;
  удаление плагина — его письма удаляются.
- **Лимиты** (значения — для обсуждения, в `[plugins]` конфигурации):
  - до 50 получателей на одно письмо, до 64 КБ данных;
  - до 10 000 писем в ящике пользователя на плагин (дальше `too-many` для отправителя);
  - частота отправки на пользователя и плагин, например 10 писем в секунду с запасом;
  - эфемерные письма удаляются по `expires_at`, в лимит ящика не входят.
- **Отключённый получатель** — письма ждут. **Отключённый плагин** — `send` и `fetch` недоступны,
  письма хранятся до включения или удаления плагина.
- **Журнал:** письма не пишутся по одному. Администратор видит на вкладке плагина сводку: сколько писем
  в ящиках, сколько эфемерных, сколько отказов по лимитам. Содержимое не показывается.
- **Приватность:** до `ack` письмо лежит в БД сервера — обычно секунды. Это тот же уровень, что
  и AppData на диске; в документации стоит сказать об этом прямо.
- **Пароли приложений** могут вызывать маршруты плагина, которые вызывают `mailbox`, — это
  понадобится будущим нативным клиентам.

### Событие для фоновых задач

Чтобы письма раскладывались, даже когда у получателя ничего не открыто:

```toml
[[jobs]]
kind = "mail"
batch = 1
on = ["mailbox"]
```

- При поступлении письма сервер ставит получателю задачу `mail` с ключом `mailbox`. Задача с тем же
  видом и ключом заменяет ожидающую, поэтому на пользователя всегда не больше одной задачи, сколько бы
  писем ни пришло.
- `run-batch` вызывается **от имени получателя**; плагин делает `fetch`, пишет в AppData, делает `ack`
  и, если писем было больше `limit`, отвечает `retry` или ставит задачу снова.
- Эфемерные письма задач не ставят: их забирает только открытая страница.

Сейчас `on` понимает только события файлов (ключ — id файла). `mailbox` — первое событие другого
рода; в манифесте и документации его стоит описать отдельно.

### Пробуждение страницы и уведомления

Панель держит одно SSE-соединение на вкладку для всех плагинов, по образцу `files/changes/watch`:

```text
GET /api/v1/apps/events
event: mailbox
data: {"app":"talk","waiting":3}

event: ring
data: {"app":"talk","from":{"id":"…","display_name":"Alice"},"text":"Звонок","letter":"…"}
```

- В событии нет содержимого писем: только какой плагин и сколько ждёт.
- **Страница плагина открыта:** панель передаёт событие странице, `rustcloud.onEvent((e) => …)`;
  страница вызывает свой маршрут, плагин делает `fetch`. Опроса нет, задержка — доли секунды.
- **Страница не открыта:** панель рисует значок с числом у пункта плагина в боковой панели (число
  неподтверждённых писем ядро знает само).
- **`ring`:** панель показывает всплывашку «Talk · Alice: Звонок» с кнопками «Открыть» и «Отклонить».
  «Открыть» ведёт на страницу плагина, `?letter=<id>`. Текст выводится как простой текст, с именем
  плагина и отправителя, которые проставляет панель, — так его не выдать за сообщение облака.
  Частоту `ring` от одного отправителя стоит ограничить отдельно.
- Лимиты SSE — как у `changes/watch` (число соединений на пользователя, переподключение по таймеру).
  При переподключении панель получает текущее `waiting` по всем плагинам.

Это не заменяет полноценные уведомления из ROADMAP (колокольчик, история, push на телефон), но
закрывает основное — «у тебя новое» — и потом может стать их частью.

### Модель угроз

| Угроза | Что защищает |
|--------|--------------|
| Плагин подделывает отправителя | `from` проставляет сервер |
| Плагин читает чужой ящик | `fetch` и `ack` — только ящик пользователя запроса в этом плагине |
| Плагин одного вида читает письма другого | ящики разделены по `app_id` |
| Спам, переполнение ящика | лимит ящика, частота отправки; блок-лист — плагином (см. открытые вопросы) |
| Перебор имён пользователей | неизвестное имя отвечает как существующее |
| Нагрузка на диск сервера | письма удаляются после `ack`, эфемерные — по TTL; ящик ограничен |
| Фишинг через всплывашку | текст без разметки, с именами плагина и отправителя от панели, ограничен по длине и частоте |

Разрешение в манифесте:

```toml
[permissions]
mailbox = true      # отправка писем другим пользователям этого плагина
```

Администратор видит при включении: «Может отправлять сообщения другим пользователям этого
приложения и показывать им уведомления».

### Рассмотренные альтернативы

- **Шифрованное общее хранилище.** Если ключ на сервере, у администратора есть и данные, и ключ:
  защищает только бэкап, а квоты, права и правило «только общее» не решает. Если ключ в браузере,
  получается полноценное сквозное шифрование (ключи устройств, восстановление, групповые ключи, никакого
  поиска на сервере) — большая отдельная работа, и JS всё равно отдаёт тот же сервер. Можно позже,
  как опцию «секретный чат» внутри плагина, поверх `mailbox`.
- **Общие коллекции с участниками** (хранилище плагина, где доступ проверяет сервер). Одна копия на
  беседу, история сразу видна новому участнику, но по сути это новая БД в ядре: схема прав, квоты
  общих данных, миграции. Больше кода и решений, чем у `mailbox`. Имеет смысл вернуться к ней, если
  появятся большие группы (сотни участников), где копирование каждому станет дорогим.

### Кому ещё пригодится

- Календарь: приглашения на встречу между пользователями облака (аналог iMIP без почты).
- Задачи и доски: «вам назначили задачу».
- Любой плагин: «с вами поделились …», ответы на комментарии.

## 2. Камера и микрофон (`permissions.media`)

### Задача

Страница плагина — `<iframe sandbox="allow-scripts allow-forms allow-downloads">` без атрибута
`allow` (`web/src/components/AppFrame.svelte`). Фрейм сервиса (`openFrame`) получает только
`clipboard-read; clipboard-write; fullscreen`. Поэтому `getUserMedia` недоступен ни странице плагина,
ни встроенному сервису.

### Предложение

```toml
[permissions]
media = ["camera", "microphone", "display-capture"]
```

- Администратор утверждает разрешение при включении плагина: «Может просить доступ к камере,
  микрофону, показу экрана».
- Панель добавляет к iframe плагина `allow="camera; microphone; display-capture"` (только
  перечисленное). Решение о доступе всё равно принимает пользователь в запросе браузера.
- В `GET /api/v1/apps` — по id плагина, как `frames` и `proxies`.

### Сначала эксперимент

Страница работает с непрозрачным origin (`sandbox` без `allow-same-origin`). Неизвестно, покажут ли
браузеры такой странице запрос разрешения или откажут сразу. Проверить в Chrome, Firefox и Safari:
тестовая страница в iframe с теми же `sandbox` и CSP, что у плагина, плюс `allow="camera; microphone"`,
вызов `navigator.mediaDevices.getUserMedia({audio: true, video: true})`.

Если не работает:

- **Вариант А (предпочтительный):** решить вопрос из ROADMAP «отдельный origin для сервисов и
  контента». Страницы плагинов отдаются со своего origin (например, `apps.cloud.example` или
  поддомен на плагин), без непрозрачного origin. Тогда работают разрешения браузера, а изоляция от
  cookie облака даже надёжнее нынешней. Цена — второй адрес и сертификат у администратора.
- **Вариант Б:** страница звонка — доверенный сервис через `openFrame` на origin облака, панель даёт
  этому фрейму `allow` по тому же разрешению. Проще, но это код на origin облака, то есть больше
  доверия плагину.

## 3. `appdata.write-if-match`

У файлов пользователя `write-if-match` есть (с 0.2.14), у AppData — нет. Плагин, который ведёт лог
в AppData (сообщения за день — один файл), может перезаписать изменение, сделанное параллельным
экземпляром (страница и фоновая задача одновременно).

```wit
/// Записать, только если файл не изменился с тех пор, как его прочитали (`etag` из `entry`);
/// иначе `conflict`. Пустой `if-match` — записать, только если файла ещё нет.
write-if-match: func(path: string, data: list<u8>, if-match: string) -> result<entry, error>;
```

`appdata.error` уже содержит `conflict`, новых типов не нужно.

## 4. Соединения страницы с сервисом (`permissions.connect`)

CSP страницы плагина — `default-src 'self'` (`crates/server/src/app_routes.rs`, `page_policy`):
страница не может открыть `wss://` к внешнему сервису. Для групповых звонков через SFU (LiveKit)
браузеру нужно соединение с ним.

```toml
[permissions]
connect = ["{livekit_url}"]     # синтаксис как у network и frame, адрес из настройки сервера

[[server_settings]]
key = "livekit_url"
kind = "text"
label = { en = "LiveKit address", ru = "Адрес LiveKit" }
```

- Адреса добавляются в `connect-src` CSP страницы; администратор утверждает их, включая плагин и
  заполняя настройку. Изменение списка при обновлении требует нового подтверждения.
- Это согласуется с исправлением из аудита (CSP страницы повторяет разрешения манифеста).

Альтернатива — режим `[[proxy]]` «любой пользователь плагина» вместо «только с открытым файлом».
Он сложнее: сервис оказывается на origin облака. Для LiveKit достаточно `connect`.

## 5. Вложения в письмах

Плагин не может открыть файл одного пользователя другому. Для вложений в чате:

```wit
record options {
    // …
    /// Файлы, выданные плагину пользователем запроса: получатели смогут читать их через этот плагин.
    attach: list<string>,
}
```

- Отправитель сам выбрал файл (он выдан плагину) и адресатов — это и есть согласие.
- Сервер выдаёт каждому получателю доступ на чтение этого файла через этот плагин (новый вид
  доступа в `grants`). Плагин получателя отдаёт файл через `links.create` или `x-rustcloud-send`.
- Доступ заканчивается, когда отправитель удаляет файл или отзывает его у плагина. Отдельно стоит
  дать отправителю список «чем я поделился через плагины» — по образцу «Общий доступ к данным
  приложений».
- Выдача попадает в журнал.

Это самый спорный пункт: он пересекается с общим доступом ядра. Его можно отложить; без него чат
работает, вложения — ссылкой на общий доступ, созданный вручную.

## 6. Звонки через TURN

### Зачем

Прямое P2P-соединение не устанавливается примерно в каждом пятом-десятом случае: симметричный NAT,
мобильный интернет (CGNAT), корпоративные сети, где открыт только TCP 443. Без TURN такие звонки
просто не соединяются. Поэтому TURN — обязательная часть звонков, а не опция.

### Что должно поддерживаться

- **Несколько серверов** — свой coturn, внешний (Cloudflare Calls, Twilio, metered.ca), или оба:
  браузер сам выбирает рабочий.
- **Все транспорты:** `turn:host:3478?transport=udp`, `turn:host:3478?transport=tcp` и
  `turns:host:443?transport=tcp` (TURN через TLS на 443 проходит почти через любой файрвол и
  прокси, которые пропускают HTTPS).
- **Временные учётные данные** по схеме TURN REST (coturn `use-auth-secret`): секрет общий у
  сервера TURN и плагина, плагин выдаёт пользователю
  `username = <expiry>:<user-id>`, `credential = base64(HMAC-SHA1(secret, username))` на несколько
  часов. Секрет в браузер не попадает, утёкшие учётные данные сами истекают. Статические логин и
  пароль — только для внешних сервисов, которые иначе не умеют.
- **Режим «только через TURN»** (`iceTransportPolicy: "relay"`): собеседники не узнают IP-адреса
  друг друга, весь трафик идёт через сервер администратора. Настройка сервера плюс, по желанию,
  переключатель пользователя «скрывать мой адрес».
- **TURN и для групповых звонков:** LiveKit использует встроенный TURN или те же внешние серверы
  (в его конфигурации), чтобы участники за строгим NAT тоже подключались.

### Вариант А: настройки плагина (без изменений ядра)

```toml
[[server_settings]]
key = "turn_servers"
kind = "list"
label = { en = "TURN servers", ru = "TURN-серверы" }
hint = { ru = "turn:turn.example.com:3478?transport=udp, turns:turn.example.com:443?transport=tcp" }

[[server_settings]]
key = "turn_secret"
kind = "secret"
label = { en = "TURN shared secret (use-auth-secret)", ru = "Общий секрет TURN (use-auth-secret)" }

[[server_settings]]
key = "turn_relay_only"
kind = "bool"
label = { en = "Relay all calls through TURN", ru = "Все звонки только через TURN" }
```

- Маршрут плагина `GET /app/talk/ice` отдаёт странице `iceServers` с учётными данными на 12 часов.
  Сеть плагину для этого не нужна: HMAC считается локально.
- На странице `status` плагин сообщает, заполнены ли настройки. Проверить сам TURN с сервера плагин
  не может (у него нет UDP), поэтому проверка — на странице плагина: кнопка «Проверить связь»
  собирает ICE-кандидаты и показывает, получен ли `relay`-кандидат по UDP, TCP и TLS.
- В установку `rc-talk` — пример `compose` с coturn: `use-auth-secret`, `realm`, диапазон портов
  ретрансляции, сертификат для `turns:` на 443 (или 5349), `denied-peer-ip` на внутренние сети
  (`10/8`, `172.16/12`, `192.168/16`, `127/8`), чтобы TURN нельзя было использовать для доступа
  в локальную сеть сервера.

### Вариант Б (по желанию): TURN в ядре

Если звонки появятся не только в `rc-talk` (видеосообщения, консультации в других плагинах),
настройки TURN лучше держать в одном месте — в конфигурации облака:

```toml
[turn]
servers = ["turns:turn.example.com:443?transport=tcp", "turn:turn.example.com:3478"]
secret = "…"           # или из переменной окружения
relay_only = false
ttl_hours = 12
```

- Импорт `use-turn.ice-servers() -> list<ice-server>` выдаёт плагину готовые учётные данные для
  пользователя запроса; секрет плагин не видит.
- Право — `use = ["turn"]` в манифесте, утверждает администратор (как `use.ffmpeg`).
- Вкладка «Сервер» в администрировании показывает, настроен ли TURN.

Для первой версии достаточно варианта А; вариант Б — когда появится второй плагин со звонками.

### TURN и CSP

Соединения WebRTC с TURN не проходят через `connect-src`, поэтому сегодня отдельного разрешения
для них не нужно. Если после проверки из следующего раздела облако начнёт ограничивать WebRTC для
страниц плагинов, разрешение на звонки (`permissions.media`) должно включать и список TURN-серверов
(из настроек), с которыми странице можно соединяться.

---

## Замечание по безопасности: WebRTC и CSP

Насколько известно, CSP почти не ограничивает WebRTC: `RTCPeerConnection` к произвольному STUN/TURN
устанавливается мимо `connect-src`. Тогда исправление из аудита («страница плагина не может унести
данные», `SECURITY_AUDIT_2026-11-14.md`) неполное: любая страница плагина может вывести данные через
канал данных WebRTC — независимо от этого предложения. Нужно проверить в браузерах (есть ли
поддержка директивы `webrtc` в CSP) и записать результат в аудит.

## Как этим воспользуется `rc-talk`

**Хранение** — в AppData каждого участника:

```text
talk/index.json                     список бесед, непрочитанное
talk/rooms/<id>/meta.json           участники, владелец, название
talk/rooms/<id>/2026-11/16.jsonl    сообщения за день (маленькие файлы — дешёвая перезапись)
```

**Чат.** Отправка — `mailbox.send(участники + себе, "msg", …)`. Письмо себе означает, что все
записи в AppData идут одним путём (фоновая задача или открытая страница), а `write-if-match`
закрывает гонки. Состав группы меняет владелец письмом `room.update`; получатели принимают его только
от владельца. Правки и удаления сообщений — только от автора. Первый контакт — по имени пользователя,
письмом «запрос на контакт»; справочник пользователей не нужен.

**Звонок один на один (mesh).** Предложение звонка — эфемерное письмо с `ring`; у получателя
всплывашка в любой части облака. Ответ SDP и ICE-кандидаты — эфемерные письма, пробуждение по SSE,
соединение — 1–2 с. Медиа — P2P, а если мешает NAT или файрвол — через TURN (раздел 6): UDP,
TCP и TLS на 443, временные учётные данные от плагина, по настройке — только через TURN. coturn
должен быть доступен из интернета: 3478 UDP и TCP, 443 или 5349 TLS, диапазон UDP-портов
ретрансляции. Mesh — до 3–4 участников.

**Групповой звонок.** LiveKit рядом с облаком (один контейнер, TURN встроен). Плагин проверяет по
AppData, что пользователь — участник беседы, и подписывает ему JWT (HS256, ключ и секрет — в
`[[server_settings]]`). Страница соединяется с LiveKit по `permissions.connect`, медиа идут по UDP
напрямую в LiveKit, а у участников за строгим NAT — через TURN (встроенный в LiveKit или тот же
coturn). Клиентская библиотека LiveKit — в архиве плагина, не с CDN.

**Без изменений ядра** плагин можно начать уже сейчас: формат хранения, интерфейс, чат с доставкой
через опрос как временную замену `mailbox`. Слой доставки потом меняется, остальное остаётся.

## Открытые вопросы

1. **Блокировка отправителей.** Достаточно, что плагин получателя игнорирует письма от
   заблокированных, или нужен `mailbox.block(user)` на сервере, чтобы письма не занимали ящик?
2. **Справочник пользователей** (поиск по префиксу, только участники общих групп, с лимитом
   частоты). Для `rc-talk` не обязателен (контакт — по имени), но удобен. Отдельное предложение?
3. **Лимиты `mailbox`** — 50 получателей, 64 КБ, 10 000 писем: подходят ли? Нужны ли они в
   `[plugins]` конфигурации или в «Системных» настройках плагина?
4. **Отдельный origin страниц плагинов** — если эксперимент с камерой не удастся, этот вопрос из
   ROADMAP становится блокирующим для звонков.
5. **Push на телефоны** — позже, вместе с уведомлениями из ROADMAP и нативными клиентами; `ring`
   стоит проектировать так, чтобы потом отправлять его и туда.
6. **Вложения** (п. 5) — делать через плагины или ждать расширения общего доступа ядра?
7. **TURN** (п. 6) — хватит настроек плагина или сразу делать `[turn]` в ядре? Включать ли
   «только через TURN» по умолчанию (приватнее, но весь трафик звонков идёт через сервер)?
