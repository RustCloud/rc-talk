# rc-talk: устройство

Плагин общения для RustCloud: личные и групповые чаты между пользователями облака, звонки через
LiveKit. Что плагин берёт у ядра (API 0.2.19) — в `docs/dev/plugins.md` RustCloud.

## Модули

| Файл | Что делает | Вызовы хоста |
|------|------------|--------------|
| [src/lib.rs](../src/lib.rs) | маршруты: страница, `/api/…`, `/status` | `settings` |
| [src/api.rs](../src/api.rs) | JSON API страницы (таблица маршрутов — в начале файла) | через `store`, `delivery`; `http` к LiveKit |
| [src/model.rs](../src/model.rs) | форматы: конверт, контакты, беседы, сообщения | нет — тесты на хосте |
| [src/inbox.rs](../src/inbox.rs) | правила получателя: что принять от кого | нет — тесты на хосте |
| [src/store.rs](../src/store.rs) | AppData пользователя | `appdata` |
| [src/delivery.rs](../src/delivery.rs) | доставка другим пользователям | `storage`, `settings` |
| [src/livekit.rs](../src/livekit.rs) | токены и запросы к LiveKit | нет — тесты на хосте |
| [ui/](../ui) | страница: список, беседа, диалоги | `rustcloud.fetch` |

Логика, в которой легко ошибиться (кто кому может писать, размеры, токены), — в чистых модулях и
покрыта `cargo test`.

## Кто есть кто

- **Человек — это id аккаунта.** После удаления аккаунта его имя может занять другой человек, и по
  имени он получил бы чужие беседы, ожидающие сообщения и вход в звонки. Контакты, участники,
  владелец группы, автор сообщения, адрес доставки и identity в LiveKit — id.
- **Имя пользователя (логин)** только показывается. По имени отправляется лишь запрос на контакт:
  id человека приходит вместе с ответом.
- **Отображаемое имя** никогда не показывается одно: его меняет сам пользователь, и назваться можно
  «Администратор». Везде «Имя (логин)» или логин ([`Person::label`](../src/model.rs)), в том числе
  в `name` токена LiveKit.
- Имена участников группы сначала со слов владельца, а когда участник пишет, их заменяет то, что
  дал сервер (`Sender`).

## Данные

Всё личное — в AppData каждого участника (`.appdata/rc-talk/`), у каждого своя копия:

```text
state.json                      {contacts: id → {state, username, display_name, since},
                                 asked: username → since,
                                 rooms: id → {peer | members, owner, names, title, last_at, last_text, unread, left}}
rooms/<id>/<YYYY-MM-DD>.jsonl   сообщения беседы за день (UTC), по строке на сообщение
```

- Контакты и беседы — в одном файле: изменение того и другого (принять контакт и открыть личную
  беседу) записывается одним `write-if-match`. Talk 0.1 держал `contacts.json` и `rooms.json`;
  их читают, пока нет `state.json`, и удаляют, когда он записан.
- В AppData одного пользователя одновременно пишут его страница и задача доставки (две задачи —
  никогда: `one_batch_per_user`). Поэтому каждая запись — `write-if-match` с etag, с которым файл
  прочитали; при `conflict` изменение делается заново поверх чужого ([store.rs](../src/store.rs)).
  Запрос страницы сначала проверяет и отправляет, а потом меняет состояние через `store::update`:
  повтор изменения ничего не отправляет второй раз.

- Личная беседа — `d` + 24 hex от SHA-256 пары id: у обоих один и тот же id. Группа — `g` + 32
  случайных hex.
- Сообщения хранятся по дням: каждая запись в AppData — новый блоб целиком, так перезаписывается
  только файл одного дня. Порядок — по времени, при равенстве по id (так советуют разработчики:
  повторная попытка задачи может выполниться позже следующих).
- Повторная доставка безвредна: сообщение с тем же id не добавляется второй раз.

## Конверт

Всё, что один пользователь отправляет другим, — [`Envelope`](../src/model.rs): `v`, `id`
(уникален для каждого действия, будущий ключ задачи), `sent_at`, `kind` и поля вида:
`contact_request`, `contact_accept`, `room_invite`, `room_update`, `room_leave`, `msg`, `msg_edit`,
`msg_delete`.

- Отправителя в конверте нет: его (с id) проставляет сервер, `jobs.origins()`.
- Конверт — не больше 64 КБ JSON (лимит `data` у `add-for`). Текст режется на сообщения по 16 КБ
  JSON с учётом экранирования. `data` у задач — строка: двоичное понадобится передавать в base64.

## Правила получателя ([inbox.rs](../src/inbox.rs))

- От незнакомого принимается только `contact_request`. Автоответов нет: ответ выдал бы, что имя
  существует. Контакт появляется, когда получатель сам нажал «Принять» (или оба попросили друг друга).
- От заблокированного не принимается ничего.
- Группу создаёт только приглашение её владельца, если он принятый контакт; менять её может только
  владелец; выйти участник может только сам; писать — только участники. Исключённый видит историю,
  но новое не получает. В группе не больше 50 человек (лимит получателей `add-for`).
- Правка и удаление — только своих сообщений (проверяется по автору в файле дня).
- `room_invite` не может занять id личной беседы.
- То же правило «кто вправе просить» будет и для отзыва вложений из задачи (см. «Вложения»).

## Доставка ([delivery.rs](../src/delivery.rs))

`jobs.add-for(получатели, {kind: "envelope", key: envelope.id, data})` (API 0.2.19): по задаче на
получателя, до 50 за вызов. Ключ — id конверта, поэтому следующий конверт не заменяет ожидающий.
Запрос на контакт уходит по логину, всё остальное — по id.

- Задача выполняется от имени получателя (`run_batch`) с урезанными правами: только AppData,
  `jobs`, настройки, журнал, `notify.badge` и `shares.unshare`. Даже если её поставил сам
  пользователь.
- Кто и когда поставил — `jobs::origins()`, по записи на задачу; оба поля проставляет сервер.
  Повтор задачи сохраняет `created_at`, поэтому порция сортируется по нему, потом применяется
  `inbox::apply` → `store::update` → `store::carry_out` (файлы дней). Ошибка записи — `retry` всей
  порции: повторная доставка безвредна, кроме того, что счётчик непрочитанного может вырасти лишний раз.
- Кому нельзя (нет такого, заблокировал, администратор не пускает) — не доходит ничего, а
  отправитель получает тот же ответ. Отправитель ставит до 1000 задач в минуту, дальше — `429
  TOO_MANY`, страница просит подождать.
- **Кто кому может писать** решает администратор в системных настройках плагина: всем или только
  с общей группой (по умолчанию).
- **Блокировка** — и в книге контактов, и на сервере (`jobs::block`): от заблокированного не
  ставятся задачи и звонки, ожидающие удаляются. «Удалить» заблокированного — `jobs::unblock`.
- **Значок** у пункта в боковой панели — непрочитанные и запросы (`notify.badge`): после доставки,
  прочтения, ответа на запрос.
- Открытая страница узнаёт о доставке по событию `changed` (`rustcloud.onEvent`) и перечитывает
  состояние; при возврате на вкладку — тоже. Открытая беседа сразу отмечается прочитанной.
- `one_batch_per_user = true`: порции одного пользователя не идут одновременно.

## Звонки

Все звонки, в том числе вдвоём, — комнаты LiveKit `talk-<id беседы>`.

- `POST /api/rooms/<id>/call` проверяет, что пользователь участник беседы, и отдаёт
  `{url, token, room}`. Identity — id аккаунта, name — «Имя (логин)».
- **Токен — на 5 минут.** LiveKit проверяет токен только при входе, а SDK сам продлевает его, пока
  соединение живо. Длинный токен позволил бы исключённому войти в звонок ещё несколько часов.
- **Исключение из идущего звонка:** когда владелец убирает участника из группы, плагин вызывает
  RoomService `RemoveParticipant` через `http` (настройка `livekit_api_url`,
  `network = ["{livekit_api_url}"]`).
- TURN — встроенный в LiveKit или тот же coturn в его конфигурации. Все соединения идут через
  LiveKit, поэтому собеседники не видят IP-адресов друг друга. В примере coturn: `denied-peer-ip` на
  частные сети, loopback и адрес облака, `no-multicast-peers`, `user-quota`, `total-quota`.
- **Вебхуки LiveKit** (кто вошёл, звонок закончился): `webhooks = ["/livekit"]` в корне манифеста,
  в LiveKit — адрес `https://<облако>/app/rc-talk/livekit`. Запрос приходит без пользователя, его
  `Authorization` — в заголовке `x-rustcloud-authorization`; подпись LiveKit (JWT с SHA-256 тела)
  проверяет плагин.
- **Входящий звонок:** `notify.ring(to, call, ref, ttl)` — со страницы звонящего (из задачи другого
  пользователя нельзя), до 60 получателей в минуту, ttl 5–300 с. Текст пишет панель: «Talk · логин:
  входящий звонок»; «Открыть» ведёт на страницу с `?ring=<ref>`. `notify.cancel(to, ref)` — звонящий
  положил трубку, `notify.dismiss(ref)` — ответили на другом устройстве.
- `permissions.connect = ["{livekit_url}"]` — ровно один сервер, сразу `https://` и `wss://`.
- **Ждём от ядра:** `permissions.media` — камера и микрофон в sandbox-iframe, после эксперимента с
  `getUserMedia`. Без него звонить нечем, поэтому `connect`, `webhooks` и звонки в манифест пока
  не добавлены: каждое новое разрешение снова ждёт подтверждения администратора.
- Клиентскую библиотеку LiveKit класть в архив плагина, не грузить с CDN.

## Вложения

Через `rustcloud.shareFile({ with, upload?, write? })` (API 0.2.19) — только со страницы и только
через диалог панели: пользователь выбирает файл в облаке или загружает с компьютера (в «Вложения»,
в свою квоту) и сам соглашается. Ответ — `{ id, name, size, mime_type, shares }`, `shares` — id
выданных доступов: их хранить у отправителя вместе с сообщением, чтобы потом отозвать. Отказ —
исключение. Публичная ссылка — `rustcloud.shareLink({ upload? })` → `{ id, url, name }`. Изменять
по умолчанию нельзя. Миниатюра у отправителя и получателя — `links.thumbnail(file-id)` (со страницы:
задаче `links` недоступен). Плагину доступ к файлам не нужен — `files = "none"`.

Отзыв (`unshare`) разрешат и в задаче, но только доступов, созданных этим пользователем через
Talk. Задачу может поставить другой человек, поэтому отзыв — только по праву: выйти из беседы —
сам участник, исключить — владелец, удалить сообщение — автор.
