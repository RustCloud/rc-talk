# Ответ на предложение «сообщения, события и звонки для плагинов»

2026-11-16. Ответ на `core-proposal.md`.

Спасибо за подробное предложение: задача описана честно, модель угроз есть, замечание про WebRTC и
CSP точное. Почти всё принимаем, но в другом виде. Главное правило для ядра: новая возможность не
должна расширять то, что плагин может сделать с данными пользователя без самого пользователя.
Ниже по пунктам — что делаем, что меняем и почему.

## Коротко

| # | Предложено | Решение |
|---|------------|---------|
| 1 | `mailbox` с `fetch`/`ack`/арендой | **Иначе:** доставка через очередь задач ядра (`jobs.add-for`) с урезанными правами у таких задач |
| 1 | SSE с событиями `mailbox` | **Да**, но без содержимого: «у плагина X новое» и `ring` |
| 1 | `ring` со свободным текстом | **Да, с ограничениями:** вид из списка, текст пишет панель |
| 1 | эфемерные письма для сигнализации | **Нет** в первой версии: звонки, в том числе один на один, — через LiveKit |
| 2 | `permissions.media` | **После эксперимента.** Вариант Б (код на origin облака) — нет |
| 3 | `appdata.write-if-match` | **Да** |
| 4 | `permissions.connect` | **Да**, с проверкой формата адреса |
| 5 | вложения: новый вид доступа плагина | **Иначе:** через общий доступ ядра, по диалогу панели; миниатюры для получателя |
| 6 | TURN | **Вариант А да**, `[turn]` в ядре — когда появится второй плагин со звонками |

## 1. Доставка сообщений: очередь задач вместо `mailbox`

Отдельное хранилище писем в ядре не нужно. Очередь задач уже даёт почти всё: таблицу, воркеры,
повторы, лимиты, сводку в админке, замену задачи с тем же ключом. Не хватает одного — поставить
задачу другому пользователю того же плагина.

```wit
interface jobs {
    record job {
        // …как сейчас, плюс:
        /// Кто поставил задачу. Проставляет сервер; для своих задач — сам пользователь.
        %from: user,
    }

    /// Задача каждому из `to` (id или имена) в этом плагине. Неизвестное имя молча пропадает,
    /// ответ тот же, что и для существующего.
    add-for: func(to: list<string>, job: new-job) -> result<_, error>;
}
```

```toml
[permissions]
deliver = true    # «Может отправлять данные другим пользователям этого приложения»
```

Как это работает в `rc-talk`: страница Алисы вызывает маршрут, плагин делает
`add-for(["bob", "carol", <alice>], {kind: "deliver", key: <id сообщения>, data: …})`. Задача
выполняется от имени каждого получателя и записывает сообщение в его AppData. При `workers = 1`
записи одного пользователя идут по очереди.

### Обязательные ограничения

**Урезанные права у задач от других пользователей.** Это главное. Задача Боба, которую поставила
Алиса, выполняется без Боба. Если дать ей доступы Боба (выданные папки, «все файлы»), то любая
ошибка в разборе сообщения превращается в «Алиса читает файлы Боба». Поэтому у задачи, у которой
`from` ≠ пользователь:

- есть AppData, `jobs.add-for`, `jobs.add`;
- нет `files`, `links`, `shares`, `network`, `use.*`, standing- и session-доступов.

Всё остальное плагин делает, когда пользователь сам открыл страницу. Раскладывать сообщения по
файлам беседы этого хватает.

**Лимиты:**

- до 50 получателей на вызов и до 4 КБ `data` (как у задач сейчас); длинное сообщение плагин режет
  на части или кладёт в свою AppData и передаёт ссылку на часть;
- не больше 10 000 ожидающих задач от других пользователей на получателя в плагине; дальше
  `too-many` у отправителя;
- частота `add-for` на отправителя и плагин;
- значения — в «Системных» настройках плагина, с разумными значениями по умолчанию.

**Кто кому может писать.** Сейчас пользователи облака друг друга почти не видят. Добавляем
настройку администратора на плагин: «всем пользователям» или «только тем, с кем есть общая
группа». По умолчанию — общая группа.

**Блокировка — на сервере.** `jobs.block(user)` / `jobs.unblock(user)`: задачи и `ring` от
заблокированного не ставятся, а отправитель получает тот же ответ, что и при успехе. Блокировка
только в плагине не помогает, потому что `ring` рисует панель (это ответ на открытый вопрос 1).

### Перебор имён

`add-for` отвечает одинаково для существующих и несуществующих имён. Но если плагин получателя
отвечает автоматически (подтверждение доставки, «запрос на контакт получен»), существование имени
видно по ответу. Не отвечайте автоматически на первое сообщение от незнакомого: подтверждение —
только после действия получателя.

## 1а. Пробуждение страницы и `ring`

```text
GET /api/v1/apps/events
event: changed
data: {"app":"talk"}

event: ring
data: {"app":"talk","from":{"id":"…","username":"alice"},"kind":"call","ref":"…"}
```

- `changed` отправляется, когда у пользователя в плагине выполнилась задача, которую поставил
  другой пользователь. Содержимого нет: страница перечитывает свою AppData. Открытой странице
  панель передаёт событие через `rustcloud.onEvent`, у закрытой рисует значок у пункта плагина.
- `ring` — отдельный импорт: `notify.ring(to, kind, ref)`. `kind` берётся из короткого списка
  (`call`, `message`, `invite`), текст всплывашки пишет панель на языке пользователя, например
  «Talk · alice: входящий звонок». Свободного текста нет, отправитель показывается по логину, а не
  по отображаемому имени (его меняет сам пользователь). «Открыть» ведёт на страницу плагина с
  `?ref=<ref>`. Частота `ring` от одного отправителя ограничена отдельно.
- Тот же список «кто кому может писать» и блокировки действуют и на `ring`.
- Позже `ring` пойдёт и в push на телефоны (вопрос 5), поэтому контракт сразу без HTML и без
  произвольного текста.

## 1б. Звонки: все — через LiveKit

Эфемерные письма для SDP и ICE в ядре делать не будем. Очередь задач для этого медленная, а
отдельный канал реального времени между страницами разных пользователей — новая большая
поверхность. Предлагаем вести через комнату LiveKit **все звонки, включая звонки один на один**:

- сигнализацию делает LiveKit; ядру остаются `ring` и `permissions.connect`;
- TURN встроен в LiveKit (или используется тот же coturn), режим «только через ретранслятор»
  получается сам собой — собеседники не видят IP-адресов друг друга;
- одна схема звонка вместо двух (mesh и SFU).

Цена — LiveKit нужен и для двух человек. Если после первой версии появятся данные, что mesh
действительно нужен, вернёмся к этому отдельно.

## 2. Камера и микрофон

Сначала эксперимент — согласны, от него всё зависит. Два дополнения.

**Делегирование разрешений.** В Chrome и Firefox запрос камеры из iframe идёт от имени верхнего
origin: «cloud.example хочет использовать камеру», и запоминается за ним же. Значит, если
пользователь разрешил камеру для Talk, её без нового запроса получат все плагины с `media`.
Отдельный origin страниц плагинов это не исправляет, пока страница встроена в панель. Поэтому:

- при включении администратор видит: «Камера, разрешённая одному приложению, доступна всем
  приложениям с этим правом»;
- в эксперимент добавьте проверку: два iframe с `allow="camera"`, разрешение в первом — что во
  втором.

**Вариант Б (страница звонка на origin облака через `openFrame`) — нет.** Код на origin облака с
`allow-same-origin` видит сессию пользователя и всё API: это XSS всего облака по определению.
Если эксперимент провалится, путь один — отдельный origin страниц плагинов (вопрос из ROADMAP), и
тогда он становится блокирующим для звонков.

## 3. `appdata.write-if-match`

Да, в том виде, как предложено. Ошибка `conflict` уже есть.

## 4. `permissions.connect`

Да. Требования:

- значение (в том числе из `{livekit_url}`) разбирается как один origin: схема `https` или `wss`,
  хост, необязательный порт, без `*`, пути и пробелов; иначе плагин не включается, или настройка
  не сохраняется;
- изменение списка в манифесте при обновлении — новое подтверждение.

## 5. Вложения: через общий доступ ядра

Нового вида доступа «файл через плагин» не будет: получился бы второй механизм общего доступа
рядом с основным. Вместо него страница просит ядро поделиться, а решает пользователь в диалоге
панели — как уже сделано для папок AppData (`rustcloud.share`).

```js
// Страница чата
const r = await rustcloud.shareFile({ with: ["bob", "carol"] });
// Панель: выбор файла → «Talk хочет открыть "report.pdf" для bob, carol: чтение» → [Поделиться]
// Результат: { node_id, share_ids, name, size, mime, thumbnail: true } — или отмена.
```

- **Плагину не нужен доступ к файлам.** Файл выбирают в диалоге панели, плагин получает только id
  и описание. Talk может обойтись `files = "none"`.
- **Только со страницы и только по диалогу.** Ни из WASM-кода, ни из фоновой задачи вызова нет.
- **Только свои файлы**, по умолчанию на чтение; галочка «на изменения» есть в диалоге, но
  выключена.
- **Метаданные доступа.** У каждого доступа ядро хранит, через что он создан: `app = "talk"` или
  пусто (через «Файлы»). Пользователь видит это в «Чем я поделился» («через Talk») и в «Доступные
  мне». Плагин может отозвать доступы, созданные через него (`rustcloud.unshare(share_id)`), без
  диалога: отзыв только уменьшает доступ. Это нужно при удалении сообщения и выходе участника из
  беседы.
- **Миниатюры.** Если пользователь поделился файлом, получатель видит и его миниатюру, когда она
  есть. Плагин получателя получает её через `links.thumbnail(node_id)` — подписанную ссылку на
  миниатюру, только для файлов, доступных пользователю через доступ, созданный этим же плагином.
  Содержимое файла плагину получателя недоступно: по клику файл открывается в «Файлах» ядра со
  всеми его проверками.
- То же для публичных ссылок: `rustcloud.shareLink(...)` через диалог, со сроком и паролем, как в
  ядре.

Добавлять людей в беседу плагин может только через тот же диалог: доступ для новых участников
выдаёт пользователь, а не плагин.

## 6. TURN

Вариант А принимаем: видов настроек `list` и `secret` хватает, ядру ничего не нужно. В пример
coturn добавьте, кроме `denied-peer-ip` на частные сети:

- запрет loopback и адреса самого облака (иначе TURN — прокси к облаку изнутри);
- `no-multicast-peers`, `user-quota`, `total-quota`;
- в `username` — id пользователя, а не имя: в логах coturn будет видно, чей трафик.

Если все звонки идут через LiveKit (1б), достаточно настроить TURN в LiveKit.

## WebRTC и CSP

Замечание верное: `RTCPeerConnection` идёт мимо `connect-src`, а страница может и сама перейти на
чужой адрес. Проверим поддержку CSP-директивы `webrtc` в браузерах, исправим формулировку в
аудите и документации: CSP страниц плагинов **затрудняет** вывод данных, но не **гарантирует**
его отсутствие. От предложения это не зависит.

## Ответы на открытые вопросы

1. **Блокировка** — на сервере (раздел 1).
2. **Справочник пользователей** — отдельное предложение. Для первой версии хватит контакта по
   имени.
3. **Лимиты** — значения из раздела 1, в «Системных» настройках плагина.
4. **Отдельный origin** — решается по итогам эксперимента (раздел 2).
5. **Push** — позже; контракт `ring` к этому готов.
6. **Вложения** — через общий доступ ядра (раздел 5).
7. **TURN** — настройки плагина или LiveKit. Включать ли по умолчанию «только через ретранслятор»,
   решает администратор, а при звонках через LiveKit это и так происходит.

## Порядок

С нашей стороны:

1. Эксперимент с `getUserMedia` и делегированием разрешений, проверка WebRTC против CSP.
2. `appdata.write-if-match`, `permissions.connect`.
3. `jobs.add-for` с `from`, урезанными правами, лимитами, настройкой «кто кому может писать» и
   блокировкой; SSE `changed`, значок, `notify.ring`.
4. `rustcloud.shareFile` / `shareLink` / `unshare`, поле `app` у доступов, `links.thumbnail`.
5. `permissions.media` — по итогам эксперимента.

Всё это — добавления в API (`0.2.19` и дальше), плагины на прежних версиях продолжают работать.
Уже сейчас можно делать формат хранения в AppData, интерфейс, звонки через LiveKit (`connect`
появится на шаге 2) и доставку опросом как временную замену шага 3.
